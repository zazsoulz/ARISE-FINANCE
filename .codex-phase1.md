# ARISE FINANCE — Phase 1: Financial Core Stabilization

Read `docs/ARISE_SPEC.md` first. It is the product source of truth. Read `docs/ARISE_AUDIT.md` second. Inspect the WHOLE current `index.html` before editing so connected calculations/UI are not fixed inconsistently.

Goal: stabilize the existing application financial core without doing Supabase/auth/offline-sync yet and without redesigning the product. Preserve existing visual language unless a UI change is required to correctly express financial state.

## Non-negotiable domain rules

1. User categories are arbitrary. The label `Свободные деньги` is NEVER a reserved identifier. A category with that name is ordinary and may be renamed/deleted.
2. Reserve is a separate system layer, never a user category.
3. System unallocated/free financial room is a separate numeric value, never a fake allocation/category and never inferred from a category name.
4. Transactions and their allocations are source of truth; statistics are derived.
5. There must be one consistent income-allocation calculation path and one exact whole-currency-unit rounding mechanism.
6. Do not allow money to be invented or lost. For a confirmed income: category allocations + reserve + system remainder must equal income exactly.
7. Never save an over-allocated plan.
8. Keep backwards compatibility with existing localStorage transactions where practical.

## Categories

- Canonical allocation modes are only `fixed` and `percentage` for this phase. Remove `remainder` as a user-selectable category mode and normalize legacy remainder categories safely instead of crashing.
- Default example categories for a new profile: `Обязательные расходы`, `Семья`, `Свободные деньги`. They are ordinary categories.
- Reserve remains separate.
- Percentage values are integer 1..100. UI can expose convenient presets, but no arbitrary fractional percentage values.
- Fixed categories are allocated before percentage categories.
- Percentage allocation is calculated from the distributable pool remaining after fixed allocations and any already-required higher-order system deductions in this phase.
- Category monthly limits are cumulative for the selected calendar month across ALL income transactions in that month. Example: limit 10,000; first income allocated 7,000; second income may auto-allocate at most 3,000. Reaching the limit stops future automatic allocation for that month.
- `limit=null` means no limit.
- Priority must have real effect when available money cannot satisfy all automatic category targets. Higher priority must be funded before lower priority under constrained conditions; do not merely sort UI rows. Preserve a deterministic tie-breaker.

## Reserve

- Separate from categories.
- Respect enabled/disabled state.
- Its monthly limit (if configured) must also be cumulative across the month rather than independently reapplied to every income.
- Do not force reserve when disabled.
- Reserve amount saved on each income must be explicit.

## System free remainder

- After automatic proposal, any unallocated positive amount is valid system free financial room/remainder.
- Positive remainder MUST NOT block save.
- It must be shown clearly in the income proposal.
- Over-allocation must block save with human-language feedback.
- Persist remainder on new income transactions.
- For historical income transactions lacking remainder, derive a safe fallback as max(0, income - saved allocations - saved reserve).

## Expenses

- Expense with explicit category ID reduces that category balance/statistics by ID, not by category name semantics.
- Expense with no explicit category is funded from system free financial room by default.
- If uncategorized expense exceeds available system free room, do NOT silently clamp it away. Record enough derived/statistical information to identify the unexplained excess as uncontrolled/untracked funds, consistent with the spec. Do not invent a fake category called `Свободные деньги`.
- Existing expense history must remain readable.

## Statistics / history

Audit and reconcile `monthStats`, current balances, history rendering, home widgets, expense preview, analytics and any other location that independently recomputes the same values. They must agree.

Required derived month-level concepts at minimum:
- income
- expenses
- reserve contributions
- category allocated balances after explicit category spending
- system free remainder after uncategorized spending
- uncontrolled/untracked expense amount
- operation count

Do not let one screen compute `free` differently from another.

## Income editor UX

- User sees every category allocation, reserve, and system free remainder before save.
- Manual edits recalculate remainder live.
- Positive remainder = valid.
- Negative remainder = over-allocation and save disabled/rejected.
- Human-readable messages only.
- All relevant buttons must work; no dead control introduced.

## Visual/UI constraints

Preserve ARISE premium minimalism: deep dark surfaces, restrained pastel accents, blur/glass where already appropriate, smooth meaningful transitions. Do not downgrade the UI to raw debug controls. Any new state (free remainder, uncontrolled funds, limit reached, allocation conflict) must have a coherent visual treatment consistent with the app.

Do not add decorative animation unrelated to state.

## Tests

Add a repeatable automated Node-based test suite for the financial core. It may extract/evaluate pure functions from `index.html` or refactor pure financial functions into a small standalone JS module if that can be done safely without introducing a build system. Prefer a modest separation if it materially improves testability, but do not rewrite the entire app/framework.

Test at least:
1. fixed + percentage + remainder exact conservation
2. multiple percentage categories with integer rounding: no missing unit
3. fixed commitments exceed income -> invalid human-readable conflict
4. positive unallocated remainder -> valid
5. manual over-allocation -> invalid
6. category named `Свободные деньги` behaves as ordinary category
7. legacy transaction without remainder fallback
8. uncategorized expense reduces system remainder
9. uncategorized expense beyond free remainder creates uncontrolled excess
10. explicit-category expense reduces that category, not system remainder
11. monthly category limit across two or more income transactions
12. monthly reserve limit across two or more income transactions
13. priority materially affects constrained allocation
14. zero/disabled rules
15. multiple incomes in same month aggregate consistently
