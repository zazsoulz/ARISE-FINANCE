# ARISE FINANCE — Full Application QA Audit (read-only code audit)

Read `docs/ARISE_SPEC.md` as the source of truth and `docs/ARISE_AUDIT.md` for prior findings. Inspect the ENTIRE repository and the ENTIRE current `index.html`. Do not modify application code in this task.

Create `docs/ARISE_CODE_QA.md` containing a concrete implementation QA audit, not generic advice.

Audit every user-visible screen and flow:
- registration/auth shell
- topbar/account
- profile switcher
- home
- income
- income proposal/editor
- expenses
- expense modal
- goals
- goal create/edit/fund/completion
- history/month navigation
- analytics
- settings/account/profile/categories/reserve/data backup
- import/export/reset
- mobile responsive behavior inferred from code

For every screen/control, verify:
1. visible button/control exists for a clear reason
2. event handler is actually bound
3. handler can access all expected DOM elements
4. no obvious null access after render/modal close
5. action changes correct domain state
6. persistence is called when required
7. resulting screen re-renders consistently
8. cancel/back/delete flows are coherent
9. duplicate or contradictory controls are noted
10. empty/loading/error/success states are sensible
11. labels match actual behavior
12. no dead buttons or decorative fake actions

Audit domain consistency across the UI:
- account vs finance profile separation
- categories arbitrary/no magic names
- reserve separate
- income allocation
- system remainder/free financial room
- expenses and uncontrolled funds
- goals and money conservation
- statistics/history/analytics consistency
- currencies
- localStorage/auth/security
- profile isolation
- import/export migration risks

Audit UI/visual implementation:
- consistency of spacing/radii/surfaces
- color-token usage vs hardcoded colors
- blur/glass consistency
- typography hierarchy
- button hierarchy
- icon system (or absence/inconsistency)
- interaction feedback
- animations/transitions and whether semantic
- chart/diagram quality vs ARISE premium spec
- mobile navigation/touch usability
- accessibility basics (labels, focus, contrast, semantic controls)

Audit code quality and maintainability:
- duplicated financial calculations
- duplicated render logic
- unused/dead functions/fields
- legacy fields/types
- fragile DOM assumptions
- giant-monolith risks
- places suitable for safe modular extraction
- error handling
- state normalization/migration

Classify each finding:
- P0 = data corruption/security/crash/financial math correctness
- P1 = major broken product flow or wrong domain behavior
- P2 = UX/visual/maintainability issue important before production
- P3 = polish/optimization

For every finding include:
- exact function/section/file
- observed behavior
- why it conflicts with spec or code consistency
- proposed fix direction
- dependencies / whether it should wait for another phase

Also include:
A. Screen-by-screen checklist with PASS / PARTIAL / FAIL
B. Button/control inventory with WORKING / BROKEN / UNCLEAR (as far as static code permits)
C. Top 20 highest-value fixes in recommended order
D. Safe refactor plan for breaking up `index.html` without rewriting the app/framework
E. Visual/UI backlog: icons, screens, transitions, blur, charts, diagrams, responsive states
F. Regression test scenarios needed after each phase

Do not claim runtime behavior you cannot prove statically. Clearly label items that need browser/runtime verification.

Do not change `index.html`, `schema.sql`, config, or production code. Only create/update `docs/ARISE_CODE_QA.md`, then remove `.codex-qa.md` before finishing. Commit the audit to this PR branch and ensure the PR diff actually contains the audit document.
